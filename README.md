# UE＋AI 工作流

用于 Unreal Engine 项目的需求澄清、定向系统调查、跨 AI 交接、独立审核和受控实现。

这是工作流 Skill 与审核角色配置示例，不是 UE 插件，不附带模型、子智能体运行时或安全沙箱。当前为待验证的发布候选，不保证所有客户端版本兼容。

## 工作方式

```text
S0 接入与权限核对
 → S1 定向调查
 → S2 需求澄清与冻结
 → S3 交接与候选准备
 → S4 独立审核与用户批准
 → S5 受控实现、验证与复审
 → S6 文档同步与交接
```

- 从需求相关系统入手，不默认扫描整个项目。
- 优先复用现有系统、接口和有效文档；没有合适框架时先讨论。
- 默认由 Codex 分析、ZCode 实现，但角色可由用户指定。
- 一个任务一份记录，公共系统文档持续维护，不按阶段建立七份文件。
- 候选完成后由实现端主动调用独立审核者；用户查看摘要，不必先审阅完整代码。
- 独立审核通过后仍需用户批准对应版本和范围。
- 同一工程目录仅一个写入者；共享文档也属于写入。

## 安装

安装前核对当前客户端官方文档。不要覆盖现有同名技能或角色；先备份、比较，再决定是否替换。

### Codex

1. 将完整 `skills/ue-ai-workflow` 目录复制到个人技能目录 `~/.agents/skills/ue-ai-workflow`。
2. 若需要专用审核角色，将 `adapters/codex/ue-code-reviewer.toml` 复制到 `~/.codex/agents/ue-code-reviewer.toml`。若设置了自定义 Codex 主目录，按实际配置调整角色目录。
3. 新建会话，检查技能和角色是否被发现；未发现时检查客户端支持及其实际配置目录，不把复制成功视为加载成功。
4. 核对当前调用工具是否支持角色选择，以及审核上下文是否实际只读。

Codex 角色文件没有设置一个可能被忽略的 `sandbox_mode` 来制造只读保证。若父会话可写、子角色又没有独立的只读限制，工作流会阻止合规审核，需要另行提供真正只读的审核环境。

### ZCode

1. 将完整 `skills/ue-ai-workflow` 目录复制到 `~/.zcode/skills/ue-ai-workflow`，或通过客户端支持的技能导入方式加载。
2. 将 `adapters/zcode/ue-code-reviewer.md` 复制到 `~/.zcode/agents/ue-code-reviewer.md`。
3. 在客户端检查技能和审核角色是否已启用，然后新建会话。
4. 确认审核角色实际仅具有 `Read`、`Grep`、`Glob`，没有终端、编辑、写入或 MCP 工具。

两端审核角色均由主智能体传入审核规范的可访问路径或完整内容，不依赖作者电脑路径。复制到两端的 Skill 不会自动同步；升级时核对版本或文件内容标识。

## 使用

在支持技能调用的客户端中发送：

> 使用 $ue-ai-workflow，身份：需求端。先只读接入当前 UE 项目，分析新增开宝箱功能，需求确认前不进入实现。

需求冻结并交接后，在实现端发送：

> 使用 $ue-ai-workflow，身份：实现端。读取我提供的任务记录，核对基线和写入负责人。先申请候选目录权限；候选完成后主动发起独立审核，等待我批准后再修改正式工程。

新对话继续任务：

> 使用 $ue-ai-workflow，身份：需求端。根据我提供的任务记录恢复当前阶段，只读核对变化，不沿用旧修改授权。

调用技能、指定角色和确认需求都不等于批准工程修改。需要项目路径或任务记录但无法唯一定位时，AI 应询问，不扫描整台电脑。

## 第一次使用前

先按 [验证说明](docs/VALIDATION.md) 做无工程写入的调用测试。确认真实子任务创建、角色权限、输入版本和结果，而不是只看主智能体声称“审核通过”。

需要修改项目规则时先取得批准；可参考 [可选项目规则](examples/project-rules.md)。保留项目已有文档名称和有效结构，不因使用本 Skill 全量迁移文档。

## 安全与已知限制

- Skill 是行为指导，不是文件锁、访问控制或权限沙箱。
- 独立审核不可用时暂停实现，不以主智能体自检替代。
- 不允许两个 AI 同时写同一工程；角色记录不能阻止另一个进程写入。
- 蓝图、地图和其他二进制资产需要额外可审查证据；文本读取工具不能证明资产运行正确。
- 静态审核不能替代编译、Editor、PIE、存档重载或打包验证。
- 不上传真实工程、候选补丁、私有任务记录、账号配置、日志或密钥到本仓库。
