# 审核与实现后自检

## 版本

对应工作流版本：2.5

## 个人模式：实现后自检

个人模式默认不调用独立审核，不生成文本候选，不建立候选区，也不执行角色交接。

正式写入前只核对：

- 本轮是否有明确写入授权；
- 目标文件、系统和功能是否仍在授权范围；
- 关键目标代码和已有改动是否发生影响方案的变化；
- 是否需要暂停询问用户。

正式写入后，主智能体执行以下自检，并如实报告结果：

| 检查维度 | 自检内容 |
|---|---|
| 需求覆盖 | 是否实现用户确认的目标，是否擅自增加功能。 |
| 系统与职责 | 修改位置是否属于主责系统，是否引入不必要的跨系统耦合。 |
| 复用与接口 | 是否遵循已查证接口、状态所有权、生命周期和复用结论。 |
| 正确性 | 成功、失败、取消、中断、重复触发、资源释放和事件清理。 |
| UE 风险 | 按需检查 UObject、Actor、Component 生命周期，C++／蓝图边界、输入锁、死亡清理、存档、异步加载和资产引用。 |
| 编码要求 | 新增或修改代码是否满足逐行注释和判断逻辑 Debug，日志是否避免敏感信息和高频刷屏。 |
| 范围与安全 | 是否改动未授权文件、依赖、权限配置或他人改动。 |
| 验证 | 验证是否覆盖主要风险，证据是否对应实际变更。 |

自检不是独立审核，不得表述为“审核通过”。没有执行的编译、Editor、PIE、资产或打包验证必须标记为未验证。

## 团队模式：候选与独立审核

以下规则仅在团队模式、用户明确要求独立审核，或项目规则把审核设为写入前提时使用。

### 候选形式

候选可以是对话中的完整文本补丁，也可以是用户明确授权的可访问文件或快照。

文本候选必须能核对任务、需求、基线、文件路径、修改内容、允许范围、禁止操作、验证计划和回滚计划。蓝图、地图和资产不能仅以文字操作说明视为实际可审核候选。

不要求默认创建候选目录、工作树或工程副本。允许修改对象是主要授权边界；禁止改动清单是额外下限，不是白名单。

### 条件授权

团队模式下，需求确认、生成交接提示词、正式写入和验证授权分别记录。个人模式下不适用该强制拆分。

未明确授权的团队操作不得从“按流程执行”或历史授权中推定。

### 独立审核

独立审核只有在用户明确要求、本轮授权明确包含，或项目规则要求时调用。审核者必须使用独立只读上下文，直接检查实际候选、必要源码、基线、范围和验证计划。

审核结论只返回：

- 通过；
- 需修改；
- 阻止或待证据。

审核通过不代表编译、运行或用户验收通过。

### 正式写入前后

正式写入前核对需求、候选或变更摘要、相关基线、单写入者和本轮授权。

发现影响方案的基线漂移时暂停并重新确认；不影响方案的局部变化可定向补查并留痕。

正式写入后检查实际差异、已有改动保护和验证结果。实际变更偏离已确认需求、授权范围或团队候选时，停止后续动作并重新确认；默认不强制落地后二次独立审核。

回滚属于写入操作，必须单独授权，不能重置整个工程。

## 版本化验证状态

分别记录以下状态，不互相替代：

| 状态 | 含义 |
|---|---|
| 源码检查 | 已读取或已检查实际源文件和差异。 |
| 已修改 | 已写入目标文件，但不代表编译成功。 |
| 已编译 | 已完成相关编译或链接。 |
| Editor | 已在 UE Editor 中完成配置或检查。 |
| PIE | 已在 PIE 或等价运行场景验证。 |
| 资产 | 已确认蓝图、地图、材质、动画或其他资产实际状态。 |
| 打包 | 已完成目标打包或发布验证。 |
