# 独立审核与授权

## 候选准备

先申请指定工程外候选目录的权限，说明任务、路径、允许生成的补丁／副本、允许验证和有效期。获得一次清单授权后按范围准备，不对每个文件反复提问；该权限不包含正式工程修改。

冻结以下审核元组：

- 任务 ID 与需求版本；
- 代码基线：提交号和相关未提交改动快照；无 Git 时使用可核对的相关文件／资产版本快照；
- 候选内容：补丁位置和内容哈希，或资产候选快照、变更清单及可核对标识；
- 修改对象、禁止操作、验证与回滚方案。

不能虚构哈希、审核记录、资产差异或批准记录。目录时间或“最新版”不是可靠内容标识。

## 审核输入和独立性

给审核者已确认需求、验收标准、实际候选、必要源码／资产上下文、基线、范围、项目约定及可用证据，不只给主智能体结论。

使用独立上下文和只读工具权限；审核者不修改文件、不修复候选、不批准实现。如果环境无法限制只读或无法实际启动独立审核，报告限制并暂停修改，等待可用审核环境。

## 必审清单

| 维度 | 检查内容 |
|---|---|
| 需求符合性 | 逐项对应需求和验收，识别遗漏与擅自增加功能 |
| 耦合度 | 依赖方向、循环依赖、跨系统直改内部状态、非必要反向依赖 |
| 职责边界 | 放置位置、状态所有权、公共组件是否硬编码具体玩法 |
| 复用 | 是否重复已有能力，接口与生命周期是否符合约束 |
| 复杂度 | 是否有更小的可行方案，是否过度抽象；不为降低耦合盲目加框架 |
| 正确性 | 成功、失败、取消、中断、重复触发、资源及事件清理 |
| 范围与安全 | 未授权文件／依赖／权限变更、信息泄露、危险操作 |
| 验证 | 主要风险是否覆盖，证据是否对应当前候选与环境 |

按相关性追加 UE 检查：UObject／Actor／Component 生命周期，C++／蓝图边界，网络 authority，Montage／Notify 时序，输入锁，死亡清理，存档重载，异步加载与资产引用。不要全任务套用所有专项。

## 结论和用户批准

仅输出通过、需修改、阻止／待证据三类结论。列明审核对象、问题位置、依据、影响、必须修复项、剩余风险和验证建议；没有问题时不要强行生成缺陷。

向用户展示结论、候选标识、变更范围、行为变化、风险、验证和回滚摘要，不要求展示完整代码。通过后等待用户批准，不能把沉默、旧批准或“按流程做”当作本次候选授权。

## 应用与复审

应用前复查审核元组和负责人。候选内容、相关基线、需求或范围实质变化时，暂停、重新审核并请求批准。

仅执行允许的修改和验证。实际变更后再次只读审核一致性、需求、范围和证据。复审发现问题时先报告；修复不得绕过候选审核和批准。

回滚也是写入：预先明确允许撤回哪些本任务改动，不能自动重置整个工程或覆盖他人成果；未获回滚权限时先申请。
