# 流程与定向调查

## 版本

对应工作流版本：3.5

## 任务接入

核对项目规则、实际工程路径、UE 版本、相关模块或插件、任务入口、必要基线、已有改动归属和本轮权限。

默认只读。缺少项目入口时只询问必要定位信息，不全盘搜索，不批量创建空文档。

简单任务可以在定向核对后直接回答；涉及实施时仍须本轮明确授权，不强制填写阶段编号或角色交接状态。

续接任务时先定位用户提供的唯一任务记录，或保底时用户传递的对话摘要，再定向核对必要源码、Git 状态、差异及已有改动归属；不沿用历史授权，不重新开展整轮调查。

## 项目首次接入与设置

知识库模式（有库／无库）、执行者（AgentA／AgentB）和实现偏好相互独立。所有分支共用授权、范围、编码、自检和验收限制，不能因切换模式放宽规则。

1. 先读取项目实际 `AGENTS.md` 或已指定的规则文件，检查知识库配置、任务目录及实现偏好。不得为查找入口全盘扫描，也不创建同义规则副本。
2. 没有规则文件或没有明确知识库配置时，先向用户询问本项目是否使用知识库及必要定位信息。用户确认无库后才走无库；有配置但访问失败不等于无库，先报告问题。
3. 无库时按 [项目规则与设置](documents.md#项目规则与设置) 比对已有规则。缺项先说明拟追加内容并申请授权，只追加，不修改、删除、重排原文；缺文件时先一并询问创建文件和加入所列规则，获准后再继续依赖初始化的流程。
4. 有库时读取该库约束，在对应项目模块保存设置，不直接在项目中建副本。缺项目模块时提出拟建位置、内容及任务目录，获准后创建；已有统一登记方式则沿用。已有设置一致时不重复写入。
5. 首次询问尚未明确的实现偏好：C++ 为主、编辑器配置资源、允许必要少量蓝图逻辑；或纯 C++、仅必要编辑器配置。经相应文档写入授权保存，后续只读取有效设置。变更须用户确认后追加明确替代记录，不能直接改原规则。
6. 规则冲突、路径不唯一、访问失败、权限不足或用户仅拒绝部分写入时，说明影响并按其决定处理，不能当作全部拒绝而自动启用保底。全部拒绝必要文档初始化时才启用下述保底；用户未答复不算拒绝或授权。
7. 设置位置与偏好不代表业务实施授权。普通咨询可在定向核实后结束，不为了使用 Skill 强制初始化或进入实施。

## 无文档保底机制

触发条件是用户明确全部拒绝必要规则补充、文件或项目模块创建，不是单纯路径错误、记录丢失、临时无法访问或未回复。已有项目规则强制留档时先报告冲突，不能用本机制覆盖原约束。

- 取消后续文档创建与更新，不写项目规则、任务记录或知识页，不换目录保存，也不更新已有任务文档。
- 定向读取当前需求相关源码、系统、必要配置和已有规则，继续需求确认、实施方案、用户选择执行者、一致性核对、本轮实施授权、实施、自测与对话交付，不重复扫描全工程。
- 确认需求、拒绝文档或选择执行者都不授权修改代码／资产；仍须准确列出业务实施范围并取得明确授权。验证也只执行获准部分。
- 项目实现偏好只在当前对话沿用，不承诺下次自动记住。AgentB 接手时由用户传递完整对话摘要；无法恢复关键需求就先询问，不假设共享记忆。
- 自测、用户配置与最终验收条件不变，结果及失败／阻塞在对话报告，不因无文档直接宣布完成。用户后来要求恢复文档流程时，重新确认位置与写入范围后再恢复，不偷偷补档。

## 调查与询问

调查与需求澄清同步推进，使用以下顺序：

1. 读取主系统文档和项目规则。
2. 查相关接口、实现、直接调用方、配置和必要资产入口。
3. 核对状态所有权、生命周期、清理、错误处理、重复触发和中断行为。
4. 根据证据判断涉及哪些系统、哪些现有功能，以及后续功能会使用哪些能力。
5. 只提出会改变方案、范围、风险、验收或用户取舍的问题。

每次扩大调查范围必须说明原因。只有证据表明会影响方案、范围、权限、风险或验收时，才调查新的系统。

技术事实由智能体查证；产品规则、体验取舍和本次范围由用户确认。建议、推测和未知内容不得写成已确认规则。

## 技术事实查证门槛

凡是要对 UE 项目的功能、系统、函数/API、蓝图节点、插件能力或配置方式给出具体用法、修改指令或行为结论，必须先核实其正确使用方式，不得只凭模型记忆、通用经验、名称猜测或相似案例推断。

### 多来源交叉确认

任何事实性或技术性结论，只有在至少三个彼此独立的文章或官方资料相互印证后，才能表述为“已确认”或“正确”。少于三个合格来源、来源相互矛盾，或无法判断来源是否独立时，必须明确说“目前不确定”，列出已查来源和缺口，不得将结论写成确定事实，也不得据此给出确定性实现指令。

- 来源必须直接支持同一个具体结论，并适用于当前引擎、插件、依赖和版本。
- 三个网页地址不自动等于三个独立来源。相互转载、共同复制同一原文、引用同一未核实说法的材料，只计为一个来源。
- 优先使用相关产品或依赖的官方文档、官方源码/头文件及独立技术文章；只对结论相关部分计数，不为凑足数量引用无关材料。
- 项目内源码、文档、配置、测试和运行日志用于核实“当前项目实际状态”，不能单独替代三个文章或官方资料对技术正确性的交叉确认；报告中应分别说明项目证据和外部来源。
- 产品需求、体验偏好和范围由用户确认，不伪装成外部事实；对这些事项给出的技术影响判断仍须满足三来源门槛。

1. **先查当前项目**：核对项目规则和相关文档，再读取实际声明与实现、直接调用方、配置、蓝图/资产引用或日志；按任务所需核实函数签名之外的参数语义、调用前提、所有权、生命周期、失败路径和清理行为。
2. **再查权威来源**：若当前项目无法证明引擎、插件或第三方 API 的定义与用法，查对应 UE 版本的官方文档、随引擎安装的头文件/源码，或该依赖的官方文档/源码。版本不匹配的资料只能作为线索，不能当作当前项目事实。
3. **核对适用性**：将来源版本、项目实际调用和目标情境对上；文档说明不能替代当前项目是否接入、配置或实际调用的核查。
4. **标明证据**：结论附上可定位的文件与行号、资产/配置路径、日志位置，或权威文档名称及适用版本。明确区分已查证事实、建议、推测和未验证项。
5. **遇到证据缺口就停在边界**：穷尽可访问的项目与权威来源后仍不能确认时，明确说明具体缺口；不把猜测写成指令。只有用户能提供的外部资料或产品决策才询问用户，其他可查技术事实由智能体继续查。

只讨论通用概念且不依赖具体项目用法时，可直接解释概念；但不得把概念解释包装成已验证的项目/API 操作指令。

## 唯一任务记录与执行者选择

有库和无库均支持 AgentA 独立完成或 AgentB 接手，不依赖特定产品或共享记忆。Skill 不提供存储、同步、调度或访问权限。

1. 正式任务需求与方案确认后、实施前，申请明确的任务文档写入范围，正常流程建立唯一记录，不以是否选择 AgentB 为条件。无库按用户本轮指定位置、项目已配置目录、项目内 `Docs/AI任务/` 的优先级选址；有库按知识库对应项目模块约束保存。
2. 记录采用 [统一专属任务文档](templates.md#统一专属任务文档)。方案须说明新增或扩展功能、复用／配置／扩展／新建系统、新增或修改代码、资产与配置、依赖顺序、风险和验收，不要求预先给出完整代码。
3. 创建后向用户提供准确任务路径，询问由 AgentA 继续还是交 AgentB；不得自行选择，也不另建第二份主记录。保底不创建记录，需求确认后直接在对话询问执行者。
4. AgentB 依据用户传递的路径读取唯一有效记录；保底则读取用户传递的需求与方案摘要。路径不可读、记录不唯一、关键字段缺失或任务状态不允许继续时先报告，不自行重建、选取或切换模式。
5. 执行者核对目标与验收、范围与非目标、选定方案、复用依据、新增／修改对象、风险及验证要求，只补查影响这些内容的必要当前事实。AgentA 同会话继续时利用已确认上下文，不重新筛查系统或重读整套文档。
6. 核对一致后简要报告结论及准确业务实施范围，并区分文档、代码／资产／配置及验证授权。用户一次明确确认可同时确认一致性并授权所列实施范围；仅确认需求、创建文档或选择执行者不满足门槛。
7. 关键差异、事实过期、需求变化或范围外对象先列出已确认内容、当前记录／事实、影响，等待用户决定。未经同意不改需求，不通过追加任务内容获得隐含权限。
8. 实施期间只读必要目标入口，直接修改获准正式工程，不设候选区、不逐版审批。关键冲突或超范围暂停相关动作，取得更新决定和授权后再继续。
9. 实现、自测、失败、阻塞和暂停时按授权更新同一记录，保底仅在对话交付；不得把失败标成功。需要用户配置与验收的任务按下述状态推进，不因代码完成就关闭。
10. 仅有库且在获准范围内才从记录摄取主题知识，区分事实、实测、推断与待验证；无库不自动建库。可复用框架先标待验证，实现框架或修改 Skill 须另获授权。

## 三层流程

此三层流程仅适用于 L1、L2 及以上任务，并按影响范围、失败后果和不确定性裁剪深度；它不是要求每个任务都经过三次审批。L0 明确不进入三层流程，定向核实后直接回答、解释或处理，不强制建立需求表、方案比较或文档交付。L1、L2 中的咨询、诊断或简单 Bug 也可在完成当前任务所需层级后停止；新增功能、系统扩展或跨系统改动按需走完整路径。用户已确认且没有变化的内容不重复询问。

### 第一层：需求与边界

1. 根据当前项目状态和用户目标，判断任务属于咨询、故障诊断、现有能力扩展、新功能、旧项目接入还是文档维护。
2. 澄清目标行为、使用场景、范围、非目标和验收条件；只询问会改变方案、风险、范围或验收的产品决策。
3. 将需求归类到相关系统或能力，区分已确认需求、建议、未知项；用户无法回答的代码、资产和技术事实由智能体调查。
4. 简单任务用自然语言确认即可；正式功能需求调查后形成需求表。先确认需求与方案，正常流程再经文档授权创建唯一记录并询问执行者；保底在对话承载。核对一致后通过一次明确确认取得一致性确认和准确实施范围授权。

### 第二层：证据、复用与方案

1. 依项目规则定向读取相关文档，再核对目标接口、实现、直接调用方、配置和必要资产；只在证据显示会影响方案、范围、风险或验收时扩大调查。
2. 对查到的文档引用逐项核对当前源码、配置或资产，不把文档描述等同于当前实现；结论标明证据来源与未验证缺口。
3. 判断现有系统是否能满足需求，并区分复用、配置、扩展或新建；核对涉及系统、责任边界、数据来源、功能逻辑、生命周期、风险和对既有功能的影响。
4. 根据已确认实现偏好明确功能逻辑与数据配置的边界，判断需求适合由现有代码、少量必要蓝图、DataAsset、DataTable 或已有配置机制承载。纯 C++ 不安排蓝图业务逻辑；仅在需求与证据支持时拆分，不强制新增架构。
5. 若现有能力不足，说明局部扩展或新建机制的必要性。多个真实可行方案值得比较时，先询问是否需要对比，用户同意后再比较优缺点、成本和风险并请求选择；只有一个可信方案时不凑选项。
6. 用户需要决定的框架、体验或数据配置方式，应在方案落定前确认；技术事实和当前项目能力由智能体查证，不要求用户自行猜测。
7. 正式需求表列明新增／修改功能、系统、文件、代码、配置与资产，说明复用及新增边界、影响、风险、验收和证据缺口。按所选文档路径创建记录或对话摘要、询问执行者，再核对一致性并明确取得实施授权，不自动把文档或知识页纳入代码授权。

### 第三层：实现、自检与文档

1. 获得本轮授权后，按已确认需求和文件范围读取必要目标代码并直接实施；不重复筛查整套系统或重读无关文档。出现关键事实冲突、方案变化或范围外文件需求时暂停并重新确认。
2. 完成后执行主智能体自检和本轮获准的验证，区分源码检查、编译、Editor 配置、资产、PIE 与打包证据；独立审核不默认启用。
3. 正常流程按已授权范围更新同一任务记录及确实相关的现有文档；记录新增与修改行为、配置、验证、失败及未验证项。未获文档授权时只在对话报告；保底明确取消后续所有文档写入，不额外建立恢复文件。
4. 自检与实际执行的测试通过后交付详细配置及验收清单；需要用户配置时任务仍待配置／验收。用户明确反馈约定测试通过后再更新最终结果并关闭，验证来源与未执行检查分别标注。

## 表格使用规则

表格用于范围把控、方案决策和最终结果，不是每轮沟通的固定格式。

- 小任务、单个细节和普通澄清使用自然语言，不强制表格。
- 功能涉及多个系统、功能边界需要用户把关，或后续依赖会影响当前设计时，集中展示一张功能影响表。
- 每轮只展示新增、变化和仍影响下一步的内容；不重复展示已确认且未变化的内容。
- 最终需求、实现结果和验证状态需要用简洁表格呈现。
- 存在多个合理方案且值得比较时，先询问用户是否需要方案对比；得到同意后，再用表格比较优点、缺点、成本、风险和建议。

功能影响表可按需使用以下列：

| 子功能 | 主责系统 | 协作／依赖系统 | 现有能力与证据 | 本次处理 | 后续用途与确定性 |
|---|---|---|---|---|---|

“后续用途与确定性”必须区分用户已确认、建议和未知。未来设想不自动扩大当前范围，也不自动产生预实现要求。

只有实际跨系统调用、状态传递或异步流程影响方案时，才补充调用顺序、数据内容、状态归属及失败／中断处理。

## 需求确认

不要求每轮声明“当前阶段、是否冻结、本轮是否修改文件”，也不要求为咨询、只读诊断或简单局部 Bug 创建完整需求汇总。

新增功能、系统扩展、跨系统改动或影响尚不明确的正式需求，完成定向调查后必须先提交需求表，再请求用户确认。需求表按子功能列出：

- 需求、目标边界和验收标准；
- 涉及系统及其职责；
- 复用的现有系统或能力；
- 新增或扩展的系统与选择理由；
- 拟修改的文件、代码、配置或资产；
- 修改后的影响、风险和不改动范围；
- 验证方式、未验证项和证据缺口。

需求表后的确认只确认需求与方案；正常流程经文档授权创建唯一记录，再询问 AgentA 全程完成还是 AgentB 接手，保底只在对话承载。执行者核对必要当前事实，报告一致性及准确实施范围，用户一次明确确认可同时确认一致性并授权列出的业务修改。未回复、含糊回复、仅确认需求、初始化、文档写入或选择执行者，均不满足业务实施门槛。

简单、局部、范围明确的 Bug 或轻量级问题可跳过正式需求表，同会话按风险裁剪记录；正常文档流程跨会话交接须有唯一记录，保底由用户传递摘要，均须一致性核对及本轮实施授权。只要求分析、诊断、解释或审核时保持只读。发现跨系统、重要产品决策或不明确影响时，转入正式需求表流程。

获得写入授权后，只修改获准范围。若关键事实冲突、方案改变或需要触及未列出的代码／资产／文档，暂停并向用户列明差异及影响；取得针对变化范围的明确决定和新授权后才可继续。

用户无法回答技术事实时主动查证，不让用户承担代码层面的调查。指定执行者、请求审核、交接或生成交接提示词不构成需求确认或文件写入授权；审核与实施分别取得对应授权。

## C++／蓝图协作补充

项目首次明确实现偏好并按模式存放；纯 C++ 与 C++ 为主的区别见 [项目设置](documents.md#项目设置内容与变更)。需求与方案阶段以 C++ 实施方案为主体，仍说明必要资源、配置工作量、少量蓝图逻辑的职责与理由及验收边界，不提前展开完整节点教程，也不把主体逻辑转交用户连接。

修改后先执行主智能体自检和获准的相应测试。自检失败先定位处理；已经执行的相关测试失败时，不宣称通过或跳到正常配置交付。通过后按实现偏好输出本次配置步骤：C++ 为主包含必要资源配置与少量已确认蓝图逻辑的详细节点；纯 C++ 只保留必要配置，不额外创建用于承载逻辑的蓝图。未执行的构建、Editor、运行测试仍明确标记，不把缺失能力当通过。

实施中才发现需要新增原方案之外的蓝图逻辑时，先说明理由、用户工作量及影响并取得决定，不能静默改变已确认分工。

编辑器配置步骤至少说明：

- **创建资产**：说明需要打开的项目、插件、模块或内容目录；创建 Blueprint Class、Widget Blueprint、Actor Blueprint、Anim Blueprint 或其他资产时，写出创建入口、资产名称、保存路径、命名规则、父类选择和选择该父类的工程依据
- **配置组件**：逐项写出需要添加、移除或确认的组件类型、组件名称、父子层级、相对位置、旋转、缩放、碰撞、可见性、Tick、输入、渲染和其他默认属性
- **配置变量**：逐项写出变量名称、变量类型、对象或类引用类型、容器类型、访问权限、实例可编辑、蓝图可读／可写、Expose on Spawn、默认值、范围、单位和引用来源
- **配置事件与接口**：写出需要覆写或实现的事件、函数、接口、委托和输入；说明事件入口、调用条件、执行顺序、绑定位置、解绑位置和生命周期要求
- **创建节点与连线**：对每个节点写出蓝图搜索名称、节点类型、放置位置或所在函数图；按执行顺序列出执行线连接；逐条列出数据线的来源、目标、引脚名称、类型转换和必要的 Break／Make／Promote 操作
- **说明分支行为**：逐项说明 Branch、Gate、DoOnce、Cast、IsValid、Sequence、Switch、Return、Failure 或错误分支的条件、True／False 或各执行引脚去向、失败后的清理和用户可观察结果
- **配置引用**：列出动画、蒙太奇、材质、DataAsset、DataTable、GameplayTag、Actor、组件、接口、Widget、输入映射和其他蓝图资产；说明引用入口、选择理由、缺失时的表现和是否需要保存引用
- **验证顺序**：写出节点编译、资产保存、关闭并重新打开、引用重新检查、PIE 或指定运行场景、成功路径、失败路径和预期日志／画面结果
- **证据状态**：每一步标记为已从当前工程查证、仅提供操作步骤、Editor 已实际配置、资产已实际确认或未验证；不得把操作说明写成已完成配置

配置步骤必须基于已查证的 C++ API、蓝图资产和项目约定；不能凭通用 UE 经验编造资产名、变量名、节点或默认值。未实际操作编辑器时，报告“配置步骤已提供”，不得报告“Editor 已配置”或“资产已验证”。实际 Editor 配置、资产状态和 PIE 结果继续分别记录。

配置细节只列与所选实现偏好及本任务有关的项目，不机械要求纯 C++ 方案配置蓝图节点。

## 用户配置与最终验收

需求确认时制定场景、操作、预期结果及必要异常测试；交付配置步骤时给出逐项可判断的验收清单。正常流程使用同一任务记录，保底在对话中记录：

| 阶段 | 判定及处理 |
|---|---|
| 实现完成 | 实际改动及主智能体自检已说明，已执行测试结果与未执行项分别列出；不等于最终完成。 |
| 待编辑器配置 | 配置步骤已交付，等待用户按步骤操作；没有操作证据不标已配置。 |
| 待功能验收 | 用户明确反馈配置完成，或本任务无需额外配置；等待约定清单的实际测试结果。 |
| 验证失败／部分通过／阻塞／暂停 | 如实说明完成项、失败或缺口、证据和下一步；正常流程按授权更新，保底仅对话报告。 |
| 已完成 | 用户明确反馈约定验收清单全部通过；补充最终结果并关闭，不把模糊“好了”当全部通过。 |

用户仅说“配置好了”只进入待验收；反馈含糊时询问具体配置或测试结果。默认由用户完成配置和运行验收，AI 仅执行本轮获准且确实可执行的验证；如果 AI 已执行测试，也向用户报告证据，不能假装收到用户确认。

用户测试记为“用户反馈验收通过”，AI 实际操作并观察到结果才记“AI 实测通过”。普通任务不强制每项截图或日志，异常、含糊或关键风险时索取必要证据；未覆盖的构建、Editor、PIE、平台等检查保持未验证，不能以用户反馈扩大证据范围。

## L0、L1、L2

| 等级 | 判断依据 | 调查与输出 |
|---|---|---|
| L0 | 查询、解释、单个细节或低影响局部任务。 | 定向核对后直接回答或实施；不强制制表、建记录或生成交接提示词。 |
| L1 | 普通功能或已有系统扩展。 | 核对相关系统、复用方式、关键异常和针对性验证；正式需求按需求表、任务记录或保底路径及明确实施授权推进。 |
| L2 | 公共系统、存档、网络、复杂时序或跨系统状态。 | 补充所有权、时序、异常矩阵和回归范围；协作按明确选择，独立审核须用户单独明确要求。 |

分级依据是影响范围、失败后果和不确定性，不是文件数量。

## 调查边界

1. 先查主系统文档，再查相关接口、实现、直接调用方、配置和必要资产。
2. 只扩大到会影响方案、范围、权限、风险或验收的系统。
3. 核对接口语义、状态所有权、生命周期、清理、错误处理、重复触发和中断行为。
4. 蓝图、地图和资产不能仅凭文本说明视为已完成或已验证。
5. 纯咨询、只读诊断和只读审核完成请求后停止，不强制进入实现。
