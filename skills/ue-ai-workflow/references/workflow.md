# 流程与定向调查

## 版本

对应工作流版本：3.0

## S0：任务接入

核对项目规则、实际工程路径、UE 版本、相关模块或插件、任务入口、必要基线、已有改动归属和本轮权限。

默认只读。缺少项目入口时只询问必要定位信息，不全盘搜索，不批量创建空文档。

个人模式下，简单任务可以在定向核对后直接回答或实施；团队模式下，使用 S0–S6 记录阶段和交接状态。

续接任务时优先查看当前源代码、Git 状态和差异，再按需要补查任务记录；不沿用历史授权。

## S1：调查与询问

调查与需求澄清同步推进，使用以下顺序：

1. 读取主系统文档和项目规则。
2. 查相关接口、实现、直接调用方、配置和必要资产入口。
3. 核对状态所有权、生命周期、清理、错误处理、重复触发和中断行为。
4. 根据证据判断涉及哪些系统、哪些现有功能，以及后续功能会使用哪些能力。
5. 只提出会改变方案、范围、风险、验收或用户取舍的问题。

每次扩大调查范围必须说明原因。只有证据表明会影响方案、范围、权限、风险或验收时，才调查新的系统。

技术事实由智能体查证；产品规则、体验取舍和本次范围由用户确认。建议、推测和未知内容不得写成已确认规则。

## 技术事实查证门槛

凡是要对 UE 项目的功能、系统、函数/API、蓝图节点、插件能力或配置方式给出具体用法、修改指令或行为结论，必须先核实其正确使用方式，不得只凭模型记忆、通用经验、名称猜测或相似案例推断。

1. **先查当前项目**：核对项目规则和相关文档，再读取实际声明与实现、直接调用方、配置、蓝图/资产引用或日志；按任务所需核实函数签名之外的参数语义、调用前提、所有权、生命周期、失败路径和清理行为。
2. **再查权威来源**：若当前项目无法证明引擎、插件或第三方 API 的定义与用法，查对应 UE 版本的官方文档、随引擎安装的头文件/源码，或该依赖的官方文档/源码。版本不匹配的资料只能作为线索，不能当作当前项目事实。
3. **核对适用性**：将来源版本、项目实际调用和目标情境对上；文档说明不能替代当前项目是否接入、配置或实际调用的核查。
4. **标明证据**：结论附上可定位的文件与行号、资产/配置路径、日志位置，或权威文档名称及适用版本。明确区分已查证事实、建议、推测和未验证项。
5. **遇到证据缺口就停在边界**：穷尽可访问的项目与权威来源后仍不能确认时，明确说明具体缺口；不把猜测写成指令。只有用户能提供的外部资料或产品决策才询问用户，其他可查技术事实由智能体继续查。

只讨论通用概念且不依赖具体项目用法时，可直接解释概念；但不得把概念解释包装成已验证的项目/API 操作指令。

## 个人模式三层流程

此三层流程仅适用于 L1、L2 及以上任务，并按影响范围、失败后果和不确定性裁剪深度；它不是要求每个任务都经过三次审批。L0 明确不进入三层流程，定向核实后直接回答、解释或处理，不强制建立需求表、方案比较或文档交付。L1、L2 中的咨询、诊断或简单 Bug 也可在完成当前任务所需层级后停止；新增功能、系统扩展或跨系统改动按需走完整路径。用户已确认且没有变化的内容不重复询问。

### 第一层：需求与边界

1. 根据当前项目状态和用户目标，判断任务属于咨询、故障诊断、现有能力扩展、新功能、旧项目接入还是文档维护。
2. 澄清目标行为、使用场景、范围、非目标和验收条件；只询问会改变方案、风险、范围或验收的产品决策。
3. 将需求归类到相关系统或能力，区分已确认需求、建议、未知项；用户无法回答的代码、资产和技术事实由智能体调查。
4. 简单任务用自然语言确认即可；正式功能需求在定向调查后形成需求表，并同时请求需求确认与表内写入授权。

### 第二层：证据、复用与方案

1. 依项目规则定向读取相关文档，再核对目标接口、实现、直接调用方、配置和必要资产；只在证据显示会影响方案、范围、风险或验收时扩大调查。
2. 对查到的文档引用逐项核对当前源码、配置或资产，不把文档描述等同于当前实现；结论标明证据来源与未验证缺口。
3. 判断现有系统是否能满足需求，并区分复用、配置、扩展或新建；核对涉及系统、责任边界、数据来源、功能逻辑、生命周期、风险和对既有功能的影响。
4. 明确功能逻辑与数据配置的边界，判断需求适合由现有代码、蓝图、DataAsset、DataTable 或项目已有配置机制承载。仅在需求和项目证据支持时拆分，不为形式强制新增数据层或架构。
5. 若现有能力不足，先说明具体缺口以及局部扩展或新建机制的必要性。存在多个真实可行且会影响用户取舍的方案时，比较至少两个方案的优缺点、成本和风险，并询问用户选择；若只有一个可信方案，不凑选项，说明依据及未采用其他方向的原因。
6. 用户需要决定的框架、体验或数据配置方式，应在方案落定前确认；技术事实和当前项目能力由智能体查证，不要求用户自行猜测。
7. 正式需求表列明拟修改文件／代码／资产、复用与新增边界、影响和风险、验证方式及证据缺口。需求确认和写入授权均完成后，才进入获准的实现范围。

### 第三层：实现、自检与文档

1. 获得本轮授权后，按已确认需求和文件范围读取必要目标代码并直接实施；不重复筛查整套系统或重读无关文档。出现关键事实冲突、方案变化或范围外文件需求时暂停并重新确认。
2. 完成后执行主智能体自检和本轮获准的验证，区分源码检查、编译、Editor 配置、资产、PIE 与打包证据；独立审核不默认启用。
3. 功能完成后，若本轮授权范围包含相关项目文档，把实际行为、适用范围、涉及系统、配置方式、使用步骤、验证结果和未验证事项补入对应文档。优先更新现有文档或按项目约定创建任务文档，不为简单局部问题重复造文档；文档只描述已查证或已完成的事实。文档未获授权时，仅列明建议补充的内容，不直接修改。
4. 交付时总结改动、验证证据、风险和下一步；涉及 C++／蓝图协作时，将编辑器操作步骤与实际 Editor 配置状态分开报告。

## 表格使用规则

表格用于范围把控、方案决策和最终结果，不是每轮沟通的固定格式。

- 小任务、单个细节和普通澄清使用自然语言，不强制表格。
- 功能涉及多个系统、功能边界需要用户把关，或后续依赖会影响当前设计时，集中展示一张功能影响表。
- 每轮只展示新增、变化和仍影响下一步的内容；不重复展示已确认且未变化的内容。
- 最终需求、实现结果和验证状态需要用简洁表格呈现。
- 存在多个合理方案且值得比较时，先询问用户是否需要方案对比；得到同意后，再用表格比较优点、缺点、成本、风险和建议。

功能影响表可按需使用以下列：

| 子功能 | 主责系统 | 协作／依赖系统 | 现有能力与证据 | 本次处理 | 后续用途与确定性 |
|---|---|---|---|---|---|

“后续用途与确定性”必须区分用户已确认、建议和未知。未来设想不自动扩大当前范围，也不自动产生预实现要求。

只有实际跨系统调用、状态传递或异步流程影响方案时，才补充调用顺序、数据内容、状态归属及失败／中断处理。

## 需求确认

个人模式下，不要求每轮声明“当前阶段、是否冻结、本轮是否修改文件”，也不要求为咨询、只读诊断或简单局部 Bug 创建完整需求汇总。

新增功能、系统扩展、跨系统改动或影响尚不明确的正式需求，完成定向调查后必须先提交需求表，再请求用户确认。需求表按子功能列出：

- 需求、目标边界和验收标准；
- 涉及系统及其职责；
- 复用的现有系统或能力；
- 新增或扩展的系统与选择理由；
- 拟修改的文件、代码、配置或资产；
- 修改后的影响、风险和不改动范围；
- 验证方式、未验证项和证据缺口。

在需求表后明确询问用户是否确认需求并授权表中列出的修改范围。只有用户明确确认需求且明确授予表内文件／资产写入权限，才可进入实现。若问题已明确同时询问这两项，用户回复“确认”可作为对该问题的肯定答复；未回复、含糊答复、仅确认需求或仅授权角色分工均不满足门槛。

简单、局部、范围明确的 Bug 修复或轻量级问题可跳过正式需求表，但必须有用户本轮明确的代码／资产修改授权。只要求分析、诊断、解释或审核时保持只读。若调查或实现揭示任务实际涉及跨系统、重要产品决策或不明确影响，则转入正式需求表流程。

获得写入授权后，只修改获准范围。若关键事实冲突、方案改变或需要触及未列出的文件／资产，暂停，更新需求表并重新询问确认和授权；不能用原授权推定新增范围获准。

用户无法回答技术事实时主动查证，不让用户承担代码层面的调查。角色分工、指定实现者、审核者、S3 交接或交接提示词只定义协作责任，不构成需求确认或文件写入授权。

## C++／蓝图协作补充

当功能修改涉及 C++ 与蓝图交接、蓝图资产、编辑器配置、组件默认值、事件绑定或资产引用时，修改完成后先执行主智能体自检。只有自检通过，才输出本次改动对应的编辑器配置步骤。

编辑器配置步骤至少说明：

- **创建资产**：说明需要打开的项目、插件、模块或内容目录；创建 Blueprint Class、Widget Blueprint、Actor Blueprint、Anim Blueprint 或其他资产时，写出创建入口、资产名称、保存路径、命名规则、父类选择和选择该父类的工程依据
- **配置组件**：逐项写出需要添加、移除或确认的组件类型、组件名称、父子层级、相对位置、旋转、缩放、碰撞、可见性、Tick、输入、渲染和其他默认属性
- **配置变量**：逐项写出变量名称、变量类型、对象或类引用类型、容器类型、访问权限、实例可编辑、蓝图可读／可写、Expose on Spawn、默认值、范围、单位和引用来源
- **配置事件与接口**：写出需要覆写或实现的事件、函数、接口、委托和输入；说明事件入口、调用条件、执行顺序、绑定位置、解绑位置和生命周期要求
- **创建节点与连线**：对每个节点写出蓝图搜索名称、节点类型、放置位置或所在函数图；按执行顺序列出执行线连接；逐条列出数据线的来源、目标、引脚名称、类型转换和必要的 Break／Make／Promote 操作
- **说明分支行为**：逐项说明 Branch、Gate、DoOnce、Cast、IsValid、Sequence、Switch、Return、Failure 或错误分支的条件、True／False 或各执行引脚去向、失败后的清理和用户可观察结果
- **配置引用**：列出动画、蒙太奇、材质、DataAsset、DataTable、GameplayTag、Actor、组件、接口、Widget、输入映射和其他蓝图资产；说明引用入口、选择理由、缺失时的表现和是否需要保存引用
- **验证顺序**：写出节点编译、资产保存、关闭并重新打开、引用重新检查、PIE 或指定运行场景、成功路径、失败路径和预期日志／画面结果
- **证据状态**：每一步标记为已从当前工程查证、仅提供操作步骤、Editor 已实际配置、资产已实际确认或未验证；不得把操作说明写成已完成配置

配置步骤必须基于已查证的 C++ API、蓝图资产和项目约定；不能凭通用 UE 经验编造资产名、变量名、节点或默认值。未实际操作编辑器时，报告“配置步骤已提供”，不得报告“Editor 已配置”或“资产已验证”。实际 Editor 配置、资产状态和 PIE 结果继续分别记录。

团队模式下同样执行上述门槛：正式需求在 S2 提交需求表并取得需求确认与表内写入授权后方可进入 S5；S3 交接本身不构成批准。简单局部 Bug 可跳过正式需求表，但仍需本轮明确授权。团队模式可按需使用完整调查表、已确认规则表、待确认边界表和冻结汇总；详细字段见 [共用模板](templates.md)。

## L0、L1、L2

| 等级 | 判断依据 | 调查与输出 |
|---|---|---|
| L0 | 查询、解释、单个细节或低影响局部任务。 | 定向核对后直接回答或实施；不强制制表、建记录或生成交接提示词。 |
| L1 | 普通功能或已有系统扩展。 | 核对相关系统、复用方式、关键异常和针对性验证；实施前输出简短变更摘要。 |
| L2 | 公共系统、存档、网络、复杂时序或跨系统状态。 | 补充所有权、时序、异常矩阵、回归范围和更严格验证；必要时使用团队模式或独立审核。 |

分级依据是影响范围、失败后果和不确定性，不是文件数量。

## 团队模式的完整阶段

团队模式保留以下内部阶段：

| 阶段 | 工作 | 推进条件 |
|---|---|---|
| S0 | 恢复项目、任务、角色、基线和权限上下文。 | 定位任务并列出关键缺口。 |
| S1 | 定向调查文档、源码、配置、资产、接口和依赖。 | 给出有证据的能力、缺口和复用结论。 |
| S2 | 确认目标、范围、行为、异常和验收。 | 用户确认关键未决项已处理。 |
| S3 | 仅在跨角色或跨工具需要交接时生成实施提示词。 | 交接材料可核对，范围和验证明确。 |
| S4 | 仅按用户要求、项目规则或本轮授权进行独立只读审核。 | 审核完成或记录未启用原因。 |
| S5 | 核对目标代码，按授权修改正式工程并验证；涉及 C++／蓝图协作时，自检通过后准备编辑器配置步骤。 | 实际变更、自检和验证结果已记录；配置步骤与实际 Editor 状态分开。 |
| S6 | 汇总变更、证据、编辑器配置步骤、未验证项、风险和下一步。 | 接收者可以恢复任务状态，且能区分源码、Editor、资产和 PIE 证据。 |

## 调查边界

1. 先查主系统文档，再查相关接口、实现、直接调用方、配置和必要资产。
2. 只扩大到会影响方案、范围、权限、风险或验收的系统。
3. 核对接口语义、状态所有权、生命周期、清理、错误处理、重复触发和中断行为。
4. 蓝图、地图和资产不能仅凭文本说明视为已完成或已验证。
5. 纯咨询、只读诊断和只读审核完成请求后停止，不强制进入实现。
