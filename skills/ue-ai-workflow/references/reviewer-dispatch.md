# 审核调用约定

## 版本

对应工作流版本：3.5

本文件仅在用户单独明确要求独立审核时使用。其余情况使用 [审核与实现后自检](review.md) 的主智能体自检清单；有库／无库／保底、AgentB 接手或风险等级都不自动触发审核。

## 发起条件

独立审核仅由用户单独明确要求后发起，并限定本轮对象和只读范围。调用 Skill、确认需求、选择执行者或授权实施均不等于请求审核。

现有项目规则与上述启用条件冲突时先报告并等待裁定，不自行修改原规则，也不通过追加新条款隐性覆盖。普通自检或材料不足时，不为完成阶段表自动创建审核任务；不建立候选区或逐版审批。

## 能力检查

发起前核对：

- 审核角色是否实际加载；
- 是否能创建独立上下文；
- 是否能限制为只读工具；
- 是否能访问实际变更、差异及必要源码；
- 是否能获得真实任务标识和返回结果，且记录方式符合当前文档授权或保底的对话交付要求。

角色配置存在不等于审核能力可用。无法确认独立性或只读权限时，必须说明限制。

未启用审核时不因审核能力不可用阻塞主智能体自检与获准实施。用户单独明确设置审核为实施前提时，不可用则报告限制并等待决定；只有用户明确允许替代时才能改变此前提，自检始终不能称作独立审核。

## 输入包

传递：

- 任务 ID、当前阶段和工作流版本；
- 需求版本、已确认需求和验收标准；
- 项目规则、必要系统文档和源码入口；
- 代码基线及已有未提交改动归属；
- 实际变更、差异及可访问位置；
- 修改范围、禁止操作和授权范围；
- 验证、回滚、已有证据和未验证项。

要求审核者直接检查实际变更，不只看实现摘要，也不提供主智能体的预先通过判断。不假设审核者可读原会话或知识库；保底由用户传递对话摘要，不为审核另建文档。

## 内置审核派发提示词

由实现负责人填写真实材料后发送给已核实的独立只读审核角色。

```markdown
使用 $ue-ai-workflow，身份：独立审核者。只读完成本次审核，不实施、不修复、不另派审核者。

- 工作流版本：【填写】
- 审核类型：【实际变更审核／用户明确要求的复审】
- 任务 ID、需求版本、已确认需求与验收标准：【填写】
- 项目约定、必要系统文档及源码入口：【填写】
- 代码基线、已有改动及归属：【填写】
- 实际变更、差异或访问位置：【填写】
- 修改范围、禁止操作和本轮授权：【填写】
- 验证、回滚、已有证据和未验证项：【填写】
- 实际变更复审材料：【用户单独明确要求、前次结论、修订差异与证据；首审填写不适用】

直接检查实际变更和必要上下文，不只看实现摘要，也不继承主智能体的通过判断。
按审核规则检查需求符合性、调查依据、耦合、职责边界、复用、复杂度、正确性、异常清理、编码要求、权限范围和验证。
仅按需求相关性追加 UE 专项检查。
材料缺失或不可访问时列出缺口，不推定通过。
不修改文件、不执行会产生写入的验证、不联网外发项目内容、不改变权限。
返回“通过／需修改／阻止或待证据”，并列出审核对象、问题位置、依据、影响、必须修复项、风险和未验证项。
```

## 等待与结果

取得真实审核任务标识或平台等效记录，等待实际结果；正常流程只在获准文档范围记录，保底仅在对话报告。不能伪造完成或把自检写成审核。

审核失败、超时、缺证据或角色不可用时，按本轮授权处理，不无限重试。

保留审核原结论。实质修订先按需求和授权边界处理，不自动冻结、逐版审批或再次派发审核；复审仍须用户单独明确要求。

审核通过后，若本轮已授权，才能修改正式工程；若未授权，只向用户报告审核摘要并请求正式写入授权。

## 实际变更复审

默认由主智能体检查实际差异与已确认需求、实施方案和授权的一致性。

只有用户单独明确要求时才发起独立实际变更复审。发现偏离时先停止相关动作并报告差异，不把偏离当作自动派发审核的授权。
