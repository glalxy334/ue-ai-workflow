# UE 技术检查

## 使用原则

- 先遵守更高优先级指令和项目 `AGENTS.md`；本参考不能扩大本轮授权或覆盖项目约定。
- 按风险和实际改动选择检查项，不逐项机械执行。L0 只检查回答或局部改动所需的事实；L1 检查相关责任边界；L2 对跨系统、共享状态、高影响或高不确定性路径做端到端核实。
- 技术事实优先从当前工程、配置、资产、日志和可运行路径查证；无法查证时标出具体证据缺口，不把推断写成事实。
- 不因套用检查清单而重复全工程扫描、重复读取无关文档或引入额外表格、任务记录和审批门。

## 复用与归属

在新增状态、配置、基础设施或代码前，针对每项职责判断现有机制是否适用，并归类为 `reuse`、`configure`、`extend` 或 `create`。选择 `extend` 或 `create` 前，查证相关类及继承配置、活跃调用方、数据表或资产、子系统、管理器和工厂；只查与该职责有关的范围。

对非平凡跨系统改动，按需明确：

- 权威数据或配置由谁持有；
- 运行时对象由谁创建、激活和释放；
- 谁触发状态创建、刷新、消费或移除；
- C++、蓝图和资产分别承担什么职责；
- 涉及持久化或网络时，其归属和边界是什么；
- 注销、清理、重置或过期由谁负责。

现有功能只有在活跃调用路径、配置和生命周期与本需求相符时，才算可复用证据。若需求与授权范围无法同时满足，先说明冲突、最小必要范围和项目内替代方案，不自行增加镜像状态、轮询、重试、代理层或共享框架改动。

## 共享系统与异步

任务涉及多个活跃使用者或共享组件、子系统、管理器、对象池、工厂、资源加载器或公共 API 时，先确认共享所有者和调用者，再检查适用契约：

- 获取与初始化、就绪、成功和失败；
- 取消、重复调用、复用、释放及清理；
- 回调绑定和解绑、重入或执行顺序；
- 对象池复用时的旧状态，以及取消后迟到回调是否会影响新使用者；
- 异步资源在加载完成到实际使用之间由什么句柄或强引用保活。

一次性状态转换优先使用项目现有事件、委托或异步完成接口；Tick 用于确实随帧变化的连续工作。只有现有接口或迁移约束要求时才保留轮询，并说明边界。简单局部代码不要求展开共享系统契约。

## 故障调查

- 从准确错误、日志和可复现路径入手，找到最后一个确认成功的状态，区分数据、生命周期、权限、绑定、状态、配置、所有权、时序和构建集成等可能类别。
- 对会改变调查方向的多个可能根因，提出可证伪的预测；用能区分假设的最小探针验证，每次探针只改变或测量一个关键因素。无需为了凑数量输出假设清单。
- 修复根因，不以额外标志、延迟、重试、静默兜底或平行状态掩盖未证实的问题。重复出现相关失败时，回溯调用链、所有权、数据流和项目先例。
- 临时诊断遵守项目现有日志类别、级别和格式；避免在 Tick、动画或高频回调中制造噪声。清理临时探针后再交付。
- 性能问题先取得可比较的基线，再判断改动是否改善目标指标。

## C++／蓝图交付补充

触发条件：功能修改已经完成，主智能体自检已经通过，且本次改动涉及 C++ 与蓝图交接、蓝图资产、编辑器配置、组件默认值、事件绑定或资产引用。

交付编辑器配置步骤时，按当前工程证据列出：

- 创建 Blueprint Class、Widget Blueprint、Actor Blueprint、Anim Blueprint 或其他资产时的创建入口、资产名称、保存路径、命名规则、父类、父类选择理由和当前工程证据
- 组件类型、组件命名、父子层级、相对位置／旋转／缩放、碰撞、可见性、Tick、输入、渲染和其他默认属性
- 变量名称、变量类型、对象或类引用类型、容器类型、访问权限、实例可编辑、蓝图可读／可写、Expose on Spawn、默认值、范围、单位和引用来源
- 需要覆写或实现的事件、函数、接口、委托和输入，以及事件入口、调用条件、执行顺序、绑定位置、解绑位置和生命周期
- 每个蓝图节点的搜索名称、节点类型、所在图表、放置顺序、执行线连接、数据线来源与目标、引脚名称、类型转换和 Break／Make／Promote 操作
- Branch、Gate、DoOnce、Cast、IsValid、Sequence、Switch、Return、Failure 或错误分支的条件、执行引脚去向、失败清理和用户可观察结果
- 动画、蒙太奇、材质、DataAsset、DataTable、GameplayTag、Actor、组件、接口、Widget、输入映射和其他蓝图资产引用，以及引用入口、选择理由、缺失表现和保存要求
- 编译、保存、关闭并重新打开、引用复查、PIE 或指定运行场景、成功路径、失败路径和预期日志／画面结果
- 每一步的证据状态：当前工程已查证、仅提供操作步骤、Editor 已实际配置、资产已实际确认或未验证

配置步骤是交付说明，不等于实际 Editor 操作。没有实际操作编辑器时，必须分别报告“配置步骤已提供”“Editor 配置未执行”“资产状态未验证”或对应的已验证状态。不得凭通用 UE 经验编造项目资产名、父类、变量名、节点、引脚、绑定、默认值或连线；无法从当前工程查证的内容标为证据缺口。蓝图连线说明必须能让接手者按节点名称和引脚名称复现，不得只写“连接事件到函数”或“配置相关变量”。

## C++、蓝图与网络边界

- 根据项目现有职责选择 C++、蓝图、配置或资产的落点；蓝图、地图和资产的文本描述不等于已完成或已验证。
- 写入前从当前工程核实新增符号是否冲突、既有 API 的声明与实现语义、访问权限、完整签名、模块依赖和 include 先例；不得根据命名或记忆猜测。
- 仅在项目与当前功能确实联网时检查客户端/服务器职责。权威状态由项目规定的一侧校验和提交；不要把客户端输入当作事实，也不要仅为本地功能添加 RPC 或复制。
- 针对真正涉及的边界查异常路径，例如无效配置、对象失效、重复触发、异步乱序、取消、重新加载、重连或清理；不要求无关任务覆盖整个矩阵。

## 验证与交付证据

把执行过的检查与仍未验证的部分分开报告。按任务适用性分别标明：

| 证据等级 | 可支持的结论 |
|---|---|
| 源码与差异 | 已检查实际代码、接口及改动范围；不代表可以编译或运行。 |
| 编译与链接 | 目标构建通过；不代表 Editor 配置、PIE 或打包正确。 |
| Editor 与资产 | 已检查实际蓝图、地图、配置或资产状态；不代表运行时行为正确。 |
| PIE 或运行时 | 已验证指定运行路径和场景；不自动代表网络、跨会话或打包行为正确。 |
| 网络、持久化、打包或平台 | 只对实际执行并记录证据的目标范围作结论。 |

按实际风险选择成功和失败路径验证。未执行的构建、Editor、PIE、网络、持久化或打包检查明确标为未验证；自检不称为独立审核。
