# 多工具协作与能力适配

## 一份规则，显式角色

通用流程不绑定平台 API。默认 Codex 做需求、ZCode 做实现，实际对应关系由用户决定；审核者必须独立于当前实现者的自检上下文。

使用同一份受维护的 Skill 核心。不同工具加载的是副本时，交接记录中核对工作流版本或内容标识；不假设两个工具自动同步规则或聊天记忆。

安装／导入方法以当前工具文档和实际能力为准，不假设另一个工具能直接读取 Codex 专用元数据。不可用的元数据不影响通用 Markdown 指令，但加载和执行效果必须实际测试。

## 启动时核对能力

按本轮角色核对所需能力；需求分析不因缺少子智能体而阻塞，实际独立审核及工程修改必须满足对应门槛。

| 能力 | 核对与降级 |
|---|---|
| 项目读取 | 确认实际路径和可读范围，不假设已有工程访问权 |
| 独立审核 | 确认能创建独立上下文并限制只读；否则暂停实现 |
| 工程写入 | 同时满足实际工具权限、独立审核和用户批准；缺一不可 |
| UE 工具 | 确认能否读取／修改蓝图、编译、运行 Editor／PIE；不把文本说明当作执行成功 |
| 外部检索 | 确认联网及外发范围；项目事实优先从相关本地证据查证 |

不在 Skill 中内置未经验证的跨平台调用命令。没有自动交接能力时，由用户传递任务记录或交接提示词，不声称消息已送达。

## 内置角色指令

按用户明确指定的身份执行以下指令，首条进度报告简述当前角色、阶段和权限。不要求用户再次粘贴本节。项目位置、当前任务和真实授权仍须核对，缺失时只询问必要信息。

### 需求负责人

从现有概览、状态、任务记录及主系统入手，定向调查当前能力、接口、依赖和文档缺口。用一张合并场景表组织需求、证据、缺口、复用结论、待确认项与验收方式。

持续询问影响方案的产品决策；需要新框架时先讨论选择。用户确认需求后生成最终交接，明确接收方身份、当前阶段、需求版本、基线、写入负责人和权限。已有共享任务记录足够时引用入口，不要求复制整套规则。不自动准备代码或进入实现。

### 实现负责人

读取交接及必要系统文档，核对需求冻结、基线和已有改动；不重复讨论已确认且未变化的需求。关键事实冲突时报告并暂停，不自行改变需求或框架。

候选目录已授权时准备实际候选，未授权时先申请目录及所需操作权限。候选完成后冻结版本，按审核调用约定主动填充并发送内置派发提示词，等待真实独立审核结果，不等待用户再说“请审核”。

需修订时只在已授权候选范围内修订并重新送审。通过后向用户展示摘要并等待批准，不能先写正式工程。获批后实施、验证，主动发起实际变更复审；最后同步获准文档和交接记录。

### 独立审核者

核对本次审核类型、需求、候选／实际变更、基线、范围和证据，独立查看实际内容，按审核规则检查需求符合性、耦合、职责、复用、复杂度、正确性、权限及验证。

只返回审核结论、依据、问题位置、必须修复项、风险与未验证项。不修改、不修复、不批准、不代替实现者整理可写记录，也不另派审核者。输入缺失时报告具体缺口，不推定通过。

区分用户直接请求的只读审查与符合工作流门槛的独立审核。独立上下文或实际只读权限无法确认时明确限制；同一实现上下文不能通过更换身份满足独立性。

## 单写入者

同一工程目录内的代码、蓝图、资产、配置、公共文档和任务记录全部遵循单写入者。指定编译／Editor／PIE／打包的运行负责人，避免共享状态互相干扰。

只读分析可并行，但审核基于冻结候选或稳定快照。发现工程正在变化时，不把中间态结论当作最终审核。

交接顺序：

1. 原负责人在获准范围内完成记录，标明未提交改动及归属。
2. 停止写入，报告待交接；停止不等于自动移除操作系统写权限。
3. 接收方核对基线、候选和任务状态，列明差异。
4. 用户确认角色／写入负责人变更及本轮操作授权，接收方确认接手。
5. 另一方保持只读；不能自动覆盖、撤销或清理前任改动。

负责人字段和时间戳只是协作约定，不是技术锁。出现多个写入者或意外外部改动时暂停受影响操作。

## 暂不默认启用的能力

不自动创建分支／worktree、不安装依赖、不加锁脚本、不跨工具调度。需要并行实现时另行讨论隔离目录、分支与文件归属、集成负责人及验证方法；同一蓝图、地图或资产不安排双人同时修改。

与其他 UE Skill 配合时，将本 Skill 作为总流程，专项 Skill 仅提供调查／实现／蓝图／审核方法；专项阶段编号若不同，按各自出口条件映射，不能把同名 S2 当作相同授权状态。
