# UE＋AI 协作工作流

## 工作流版本

当前版本：2.8

本 Skill 是流程约定，不自动提供子智能体、跨工具调度、文件锁、UE 编辑器控制或技术权限。

## 模式选择与启动

1. 遵守更高优先级指令和适用的项目规则。项目 `AGENTS.md` 明确声明工作模式时，按其执行；否则默认使用个人模式。用户可在本轮明确要求团队模式。
2. 模式只决定协作流程，不扩大文件、写入、验证、联网或资产操作权限。
3. 判断任务是咨询、只读诊断、需求调查、实现、文档维护还是中断恢复，并按 L0、L1、L2 选择调查深度。
4. 核对项目路径、任务入口、必要基线和已有改动；默认定向读取，不扫描整个工程，不沿用历史授权。
5. 技术事实由智能体查证；产品选择、体验取舍和范围由用户决定。

进入项目时按项目 `AGENTS.md` 声明的入口和顺序定向读取；项目未声明时，默认依次读取 `AGENTS.md`、项目状态文档、相关当前文档、目标源码或资产入口、最新日志。只查本任务相关范围；日志持续变化时固定证据截点。

- L0：咨询、简单细节或低影响局部问题。定向核实后直接回答或诊断并停止，不强制建表、任务记录或进入实现。
- L1：普通功能或已有系统扩展。核对相关系统、复用方式、关键异常和针对性验证。
- L2：公共系统、存档、网络、复杂时序或跨系统状态。补充状态所有权、调用时序、异常矩阵和回归验证。

UE 技术检查按任务风险和实际改动触发，不把完整检查表变成每个任务的强制门禁。实现、故障诊断、共享系统集成或代码审核时，按需读取 [UE 技术检查](references/ue-technical-checks.md)；纯咨询和不涉及技术变更的沟通不加载该清单。

## 个人模式

个人模式是默认路径，单会话内不模拟需求负责人和实现负责人的角色交接。

1. 定向调查相关文档、源码、配置及必要资产，确认涉及的系统和现有功能；不重复筛查整个工程。
2. 按证据提出必要问题。只追问会改变方案、范围、风险或验收的产品决策；用户无法回答的技术事实由智能体查证。
3. 小任务和单项细节用自然语言沟通，不强制表格或完整需求汇总。不要要求用户重复确认未变化的内容。
4. 对新增功能、系统扩展、跨系统改动或影响尚不明确的正式需求，完成定向调查后必须先提交需求表，列明需求与验收、涉及系统、复用系统、新增或扩展系统、拟修改文件／代码／资产、变更影响与风险、验证方式及证据缺口。
5. 在需求表后明确询问用户是否确认需求并授权表中列出的写入范围。只有用户明确确认需求且明确授权这些文件／资产的修改，才可实施；未回复、含糊回复、仅确认需求或仅表示同意角色分工均不构成写入授权。
6. 简单、局部、范围明确的 Bug 修复或轻量级问题可跳过正式需求表，但仍须有用户本轮对代码／资产修改的明确授权。若请求只要求诊断、解释或审查，则保持只读。
7. 角色分工、指定负责人、S3 交接、生成实施提示词或安排审核只定义协作职责，不代表需求已确认，也不代表获得文件修改授权。团队模式同样必须遵守需求确认与写入授权门槛。
8. 获得本轮授权后，读取必要目标代码并直接修改正式工程。若关键事实冲突、方案需要改变或工作超出已授权文件／资产范围，暂停，更新受影响的需求表并重新取得明确确认和授权。
9. 修改后执行主智能体自检及本轮获准的验证；独立审核仅在用户明确要求或项目规则要求时启用。
10. 修改涉及 C++ 与蓝图、蓝图资产或编辑器配置时，只有主智能体自检通过后，才输出与本次改动对应的编辑器配置步骤；未实际操作编辑器时，必须把步骤和 Editor 已配置状态分开报告。

## 表格与方案比较

表格服务于范围把控和决策，不是每轮沟通的固定格式。

- 小任务、单个细节和普通澄清使用自然语言；不为满足流程而制表。
- 新增功能、系统扩展、跨系统改动或影响不明确的正式需求，在任何写入前必须发送需求表并询问用户。需求表至少包含：需求／子功能、验收、涉及系统、复用的系统或能力、新增或扩展的系统、拟修改文件／代码／资产、修改后的影响与风险、验证方式、未确认项或证据缺口。
- 简单局部 Bug 或轻量级问题可跳过正式需求表；这项例外不免除本轮明确写入授权，也不适用于实施过程中扩展为跨系统或影响不明确的情况。
- 需求表后的确认问题必须同时询问需求确认和表内文件／资产写入授权。用户明确回复确认该问题即可授权表内范围；仅确认需求、角色分工、交接或指定实现者均不授权写入。
- 功能任务的影响表应按子功能列出主责系统、协作系统、现有能力及证据、本次处理方式、系统依赖和后续用途。
- 后续用途区分“用户已确认”“建议”与“未知”；未确认的设想不自动扩大本次范围或成为预实现要求。
- 存在多个合理方案且比较有帮助时，先询问用户是否需要方案对比。用户同意后，再用表格比较方案、优点、缺点、成本或风险及建议。
- 功能范围、系统影响和实现交付的关键结果用简洁表格汇总。纯咨询或单点诊断无需为了形式强制表格。

功能影响表可按需使用以下列：

| 子功能 | 主责系统 | 协作／依赖系统 | 现有能力与证据 | 本次处理 | 后续用途与确定性 |
|---|---|---|---|---|---|

只有实际跨系统调用、状态传递或异步流程影响方案时，才补充调用顺序、数据内容、状态归属及失败／中断处理。

## 团队模式

团队模式仅在项目规则声明或用户本轮明确要求时使用。保留 S0–S6 作为内部阶段、任务记录、角色交接、可核对候选和独立审核等协作流程。正式需求须在 S2 形成需求表并取得需求确认及表内写入授权后，才能进入 S5；简单局部 Bug 可按个人模式例外跳过正式需求表，但仍须明确写入授权。S3 角色分工或交接不能代替 S2 批准或写入授权。只有团队交接或用户要求时才展示完整提示词或审核摘要。

| 阶段 | 工作 |
|---|---|
| S0 接入 | 恢复项目、任务、角色、基线和权限上下文。 |
| S1 调查 | 定向核实文档、源码、配置、资产、接口和依赖。 |
| S2 澄清 | 确认目标、范围、行为、异常和验收。 |
| S3 交接 | 仅在需要跨角色或跨工具交接时生成实施提示词。 |
| S4 审核 | 仅按用户要求、项目规则或本轮授权进行独立只读审核。 |
| S5 实现 | 核对目标代码，按本轮授权修改并验证。 |
| S6 交付 | 汇总变更、证据、未验证项、风险和下一步；涉及 C++／蓝图协作时，交付编辑器配置步骤及其验证状态。 |

团队模式不代表默认启用独立审核，也不假设存在子智能体、文件锁或 UE 自动化能力。详细协作规则见 [协作与能力适配](references/collaboration.md)；审核授权见 [审核与授权](references/review.md)。

## 调查与需求边界

1. 先查主系统文档，再查相关接口、实现、直接调用方、配置和必要资产。
2. 只有证据表明会影响方案、范围、权限、风险或验收时，才扩大到其他系统。
3. 核对接口语义、状态所有权、生命周期、清理、错误处理、重复触发和中断行为。
4. 区分用户确认的需求、项目查证的事实、初步建议、待确认边界和未验证项。
5. 蓝图、地图和资产不能仅凭文本说明视为已完成或已验证。
6. 纯咨询、只读诊断和只读审核完成请求后停止，不强制进入实现。

## 授权、实现与自检

- 正式需求必须先有需求表，并由用户明确确认需求及授权表内文件／资产修改；简单局部 Bug 可免需求表，但仍需本轮明确写入授权。需求确认与角色分工均不能单独扩大写入权限，历史授权不得沿用。
- 禁止改动清单是额外下限，不是白名单；未列入禁止清单不代表默认允许修改。
- Git 状态和差异可用于恢复代码基线；先保护未提交、未跟踪及他人改动。Git 不构成自动回滚授权，UE 二进制资产和文档也要核对实际状态。
- 不顺手重构、删除、迁移、升级、重置或修改权限配置。回滚属于写入操作，须单独授权。
- 新增或修改代码遵守项目 `AGENTS.md` 声明的编码、注释与日志约定；项目未声明时沿用现有代码风格，不引入新约定。
- 修改后按 [实现后自检清单](references/review.md) 检查需求覆盖、范围、依赖、职责、生命周期、失败／取消／中断、重复触发和清理。
- 分别记录源码检查、编译、Editor 配置、PIE、资产和打包状态；一种证据不替代另一种。没有执行的验证明确标为未验证。
- 涉及 C++／蓝图交接、蓝图资产或编辑器配置的功能，主智能体自检通过后补充详细编辑器配置步骤：创建 Blueprint Class 时的父类与选择理由、保存路径和命名；组件类型、命名、相对变换和默认属性；变量类型、容器类型、访问权限、默认值和暴露方式；覆写或实现的事件、函数、接口和委托；每个蓝图节点的搜索名称、放置顺序、执行线和数据线连接；Branch、Gate、Cast、Valid、Return、Failure 等分支；动画、材质、DataAsset、DataTable、Actor、组件和其他蓝图引用；编译、保存、重新打开、PIE 检查和预期结果。只提供步骤不等于已完成 Editor 配置。
- 复杂或中断任务可追加简短任务记录；简单任务不强制创建记录。文档规范见 [文档规范](references/documents.md)。

项目事实和进度保存于项目文档，不写回通用 Skill。每次任务按复杂度保留足以恢复状态的记录。
