# UE＋AI 协作工作流

## 工作流版本

当前版本：3.5

本 Skill 是流程约定，不自动提供子智能体、跨工具调度、文件锁、UE 编辑器控制或技术权限。

## 模式选择与启动

1. 遵守更高优先级指令和适用的项目规则。先读取实际项目的 `AGENTS.md` 或项目明确指定的规则文件；首次接入规则见 [项目首次接入](references/workflow.md#项目首次接入与设置)。
2. 知识库模式只区分有库与无库的内部检索、记录及沉淀方式；AgentA／AgentB 执行者与 C++ 实现偏好是独立维度。所有路径遵守同一套权限与限制。
3. 项目规则未说明知识库配置，或项目没有规则文件时，先询问用户，不能仅凭缺少配置认定无库。已配置但不可访问时报告问题，不静默切换。
4. 无库时检查项目规则，只能在明确授权后追加缺失条款；没有文件时先申请创建文件及加入规则。有库时按知识库约束在对应项目模块保存设置，缺少模块先申请，不在项目中另建副本。规则冲突先报告，不通过追加相反规则隐性覆盖。
5. 技术事实由智能体查证；产品选择、体验取舍和范围由用户决定。
6. 不得仅凭模型记忆、通用经验或相似案例，对项目功能、系统、函数/API 的存在、职责、调用方式、参数语义、生命周期或配置用法发出确定性指令；先按 [技术事实查证门槛](references/workflow.md#技术事实查证门槛) 核对证据。
7. 对事实或技术结论，至少用三个彼此独立的文章或官方资料交叉确认后，才可判定为正确；不足三个时必须明确标为“不确定”，不得写成确定结论。

首次使用时询问尚未确定的项目实现偏好：**C++ 为主，编辑器配置资源，允许必要的少量蓝图逻辑**，或**纯 C++，仅保留必要配置**。经授权按所选知识库模式保存，后续读取现有设置，不重复询问；变更只能追加用户确认的替代记录。设置不构成实施授权，详见 [项目规则与设置](references/documents.md#项目规则与设置)。

项目已声明读取顺序时按其定向读取；未声明时只读取存在且相关的项目状态、当前文档、目标源码或资产入口及必要日志，不因缺少文档推断功能不存在。核对任务入口、必要基线与已有改动；日志持续变化时固定证据截点。

统一使用下述主流程，不自动启用候选区、逐版审批或独立审核。用户全部拒绝必要文档初始化时，可进入 [无文档保底机制](references/workflow.md#无文档保底机制)，不改规则、不创建或更新任务文档，仍可在本轮明确实施授权后处理需求。原有规则强制留档时，先报告冲突，不自行绕过。

- L0：咨询、简单细节或低影响局部问题。定向核实后直接回答或诊断并停止，不强制建表、任务记录或进入实现。
- L1：普通功能或已有系统扩展。核对相关系统、复用方式、关键异常和针对性验证。
- L2：公共系统、存档、网络、复杂时序或跨系统状态。补充状态所有权、调用时序、异常矩阵和回归验证。

分级不豁免技术事实查证：即使 L0，也必须先核实答案中涉及的项目功能、函数/API 或系统的正确用法；L0 仅跳过三层需求流程和相应的正式产物。

UE 技术检查按任务风险和实际改动触发，不把完整检查表变成每个任务的强制门禁。实现、故障诊断、共享系统集成或代码审核时，按需读取 [UE 技术检查](references/ue-technical-checks.md)；纯咨询和不涉及技术变更的沟通不加载该清单。

## 主流程

单会话内不模拟需求负责人和实现负责人的角色交接；需要其他 AI 接续时，由用户选择执行者，不另设角色分工流程。

仅 L1、L2 及以上任务采用“需求与边界—证据与方案—实现与交付”三层流程，并按风险裁剪深度；L0 不进入该流程，定向核实后直接回答或处理。各层的调查顺序、复用判断和停止条件见 [流程与调查规则](references/workflow.md)。

正常文档流程中，正式任务在需求与方案确认后、实施前，经文档写入授权创建唯一任务记录，不论随后由谁执行。无库默认使用 `Docs/AI任务/`，用户指定或项目已配置的位置优先；有库按知识库及项目模块约束保存，不另建项目副本。任务创建后询问由 AgentA 继续还是交 AgentB，并输出准确任务路径。保底流程仅在对话中保留需求和交接摘要。

1. 定向调查相关文档、源码、配置及必要资产，确认涉及的系统和现有功能；不重复筛查整个工程。
2. 按证据提出必要问题。只追问会改变方案、范围、风险或验收的产品决策；用户无法回答的技术事实由智能体查证。
3. 小任务和单项细节用自然语言沟通，不强制表格或完整需求汇总。不要要求用户重复确认未变化的内容。
4. 对新增功能、系统扩展、跨系统改动或影响尚不明确的正式需求，完成定向调查后先提交需求表，列明需求与验收、涉及系统、复用系统、新增或扩展系统、拟修改文件／代码／资产、变更影响与风险、验证方式及证据缺口。
5. 用户确认需求与方案后，按正常文档流程创建唯一任务记录，再询问由 AgentA 全程完成还是交 AgentB；不得自行选择。确认需求或选择执行者不授权写入。文档内容覆盖功能新增／扩展、复用／新建系统、新增／修改代码、资产、配置、依赖顺序、风险和验收，不提前展示完整代码。
6. 实施者读取任务记录，或保底时读取用户传递的对话摘要，核对已确认需求及必要当前事实，不重复整轮调查。正常流程发现记录缺失、不唯一、不可访问或关键差异时先报告，不能自行切入保底、重建或改写需求；保底不假设跨会话共享记忆。
7. 核对一致后，实施者向用户简要报告核对结论及明确的文件／代码／资产修改范围。用户的一次明确确认同时表示“任务符合 AgentA 已确认需求”及“授权按所列范围实施”；只有该确认后才可进行对应业务实施写入。不得要求用户重复确认未变化的需求内容。
8. 简单、局部、范围明确的 Bug 或轻量级问题可跳过正式需求表，同会话按风险裁剪记录；需要交接时正常流程仍保留唯一记录。文档保底不免除一致性核对与本轮明确写入授权。只要求诊断、解释或审查时保持只读。
9. 文档初始化、指定执行者、交接或生成实施提示词均不代表授权实施。任何路径不假设自动调度、共享记忆、同步权限或文件锁。
10. 获得本轮授权后，读取必要目标代码并直接修改正式工程。若关键事实冲突、方案需要改变或工作超出已授权文件／资产范围，暂停并向用户说明；未取得更新确认和授权前不得扩大范围。
11. 修改后执行主智能体自检及获准验证，不默认调用审核子智能体；只有用户单独明确要求才启用独立审核，已有项目要求与此冲突时先询问。任务失败、阻塞或暂停时按授权更新同一记录；保底只在对话报告，不创建或更新文档。
12. 正常流程在实现及相应自测后更新结果；需要用户配置时标记待编辑器配置／待功能验收。用户按约定验收清单测试并明确反馈通过后，更新最终记录并关闭任务。用户反馈与 AI 实测分开标注，未执行检查仍为未验证。
13. C++ 为主时仅把已确认且更合适的少量逻辑留在蓝图，方案阶段说明分工、资源和验收范围，详细配置与节点步骤在实现及相应自测通过后交付；纯 C++ 路径只提供必要配置。不为未验证步骤伪造已配置状态。
14. 仅有库且获准时从任务记录摄取知识，保留来源与适用边界；单次框架先标待验证。无库不自动建库，保底不写文档；实现框架或修改 Skill 仍属新的授权范围。

## 表格与方案比较

表格服务于范围把控和决策，不是每轮沟通的固定格式。

- 小任务、单个细节和普通澄清使用自然语言；不为满足流程而制表。
- 新增功能、系统扩展、跨系统改动或影响不明确的正式需求，在业务代码／资产／配置实施写入前必须发送需求表并询问用户；项目设置初始化另按明确文档授权执行。需求表至少包含：需求／子功能、验收、涉及系统、复用的系统或能力、新增或扩展的系统、拟修改文件／代码／资产、修改后的影响与风险、验证方式、未确认项或证据缺口。
- 简单局部 Bug 或轻量级问题可跳过正式需求表；这项例外不免除本轮明确写入授权，也不适用于实施过程中扩展为跨系统或影响不明确的情况。
- 需求表后的确认只确认需求与方案。正常流程经文档写入授权建立唯一任务记录，再询问执行者；保底通过对话承载。执行者核对一致并列出准确写入范围后，用户的一次明确确认同时确认一致性并授权该实施范围；初始化和任务文档授权不能代替实施授权。
- 功能任务的影响表应按子功能列出主责系统、协作系统、现有能力及证据、本次处理方式、系统依赖和后续用途。
- 后续用途区分“用户已确认”“建议”与“未知”；未确认的设想不自动扩大本次范围或成为预实现要求。
- 存在多个合理方案且比较有帮助时，先询问用户是否需要方案对比。用户同意后，再用表格比较方案、优点、缺点、成本或风险及建议。
- 功能范围、系统影响和实现交付的关键结果用简洁表格汇总。纯咨询或单点诊断无需为了形式强制表格。

功能影响表可按需使用以下列：

| 子功能 | 主责系统 | 协作／依赖系统 | 现有能力与证据 | 本次处理 | 后续用途与确定性 |
|---|---|---|---|---|---|

只有实际跨系统调用、状态传递或异步流程影响方案时，才补充调用顺序、数据内容、状态归属及失败／中断处理。

## 调查与需求边界

1. 先查主系统文档，再查相关接口、实现、直接调用方、配置和必要资产。
2. 只有证据表明会影响方案、范围、权限、风险或验收时，才扩大到其他系统。
3. 核对接口语义、状态所有权、生命周期、清理、错误处理、重复触发和中断行为。
4. 区分用户确认的需求、项目查证的事实、初步建议、待确认边界和未验证项。
5. 蓝图、地图和资产不能仅凭文本说明视为已完成或已验证。
6. 纯咨询、只读诊断和只读审核完成请求后停止，不强制进入实现。

## 授权、实现与自检

- 正式需求先确认需求与方案，按有库／无库／保底路径承载任务，再核对一致性并列出准确实施范围，取得本轮明确授权后实施。初始化、任务文档、业务实施和验证的授权范围须区分；简单局部 Bug 可免需求表，历史授权不得沿用。
- 禁止改动清单是额外下限，不是白名单；未列入禁止清单不代表默认允许修改。
- Git 状态和差异可用于恢复代码基线；先保护未提交、未跟踪及他人改动。Git 不构成自动回滚授权，UE 二进制资产和文档也要核对实际状态。
- 不顺手重构、删除、迁移、升级、重置或修改权限配置。回滚属于写入操作，须单独授权。
- 新增或修改代码遵守适用项目规则；每行新增或修改代码均须有中文注释，有判断的代码须增加可关闭的 debug，日志不记录密钥或敏感原文。格式不支持注释时先说明并询问，不私自例外处理；其余风格沿用项目。
- 新增或修改的代码注释使用中文；API、类型、函数名等技术标识符保留原名，不为统一语言批量翻译本次范围外的已有注释。
- 修改后按 [实现后自检清单](references/review.md) 检查需求覆盖、范围、依赖、职责、生命周期、失败／取消／中断、重复触发和清理。
- 分别记录源码检查、编译、Editor 配置、PIE、资产和打包状态；一种证据不替代另一种。没有执行的验证明确标为未验证。
- 实现、主智能体自检及已执行的相应测试通过后，按项目实现偏好交付必要配置和验收清单。详细资源、组件、引用、节点与连线字段见 [C++／蓝图交付补充](references/ue-technical-checks.md)；纯 C++ 只列必要配置，不强制蓝图逻辑。只提供步骤不等于已完成 Editor 配置，未执行检查仍为未验证。
- 正式任务记录在需求确认后、实施前创建；完成、失败、阻塞和暂停时按授权更新。普通咨询不强制建档，简单局部任务按风险裁剪；保底取消后续文档创建与更新。文档规范见 [文档规范](references/documents.md)。

正常流程以所在模式的一份任务记录为主记录，跨 Agent 交接确认可读路径，不复制成第二份主记录；保底由用户传递对话摘要。项目技术事实遵守现有归属，不能用知识库设置覆盖项目约束。具体任务事实不写回通用 Skill。

## Skill 自身修改与维护日志

- 本公开发行版不包含维护者的个人知识库路径。维护前先由用户指定并授权维护知识库根目录，下文用 `{维护知识库根目录}` 表示该位置；未配置时先询问，不猜测路径或自动创建知识库。此处仅将本地 v3.5 的个人路径参数化，不改变业务工作流。
- 本节仅约束 AI 修改本 Skill 本体（`SKILL.md` 及附属文件）的维护任务，不把使用本 Skill 处理 UE 项目任务视为修改 Skill，也不改变业务任务的有库／无库／保底规则。
- 每次申请修改本 Skill 的本轮实施授权时，必须将 `{维护知识库根目录}` 内的新版本完整快照、`raw/README.md`、`wiki/来源摘要/UE-AI协作工作流.md`、`wiki/index.md` 及 `wiki/log.md` 的必要更新，一并列入同一任务的必要写入范围；获准后由实施 AI 执行。仅确认需求不触发写入，历史修改授权不延续。
- 写入前定向读取该知识库的 `AGENTS.md`、`wiki/index.md`、日志必要尾部与本来源现有摘要、收录记录。完成获准修改及相应自检后，待源目录稳定，再将最终完整 Skill 目录逐字节保存到 `raw/UE-AI协作工作流-{入口版本}-{本机日期}/`，保留所有文件、相对结构及原文，不在快照中添加摘要或注释；版本未升级时如实注明沿用，不为了入库擅自改版本号。
- 已有快照不得改写或删除。拟用目录已存在时，先核对文件清单与 SHA-256；内容完全一致则复用并注明，内容不同则新增带本机时分秒后缀的独立快照，仍有冲突时停止报告，不覆盖。复制前后核对源目录稳定性，再核对快照的文件清单与逐文件 SHA-256；源目录变化或不完整时标为未完成，不宣称版本已同步。
- 同步更新该来源的摘要、`raw/README.md` 收录清单和 `wiki/index.md` 当前版本入口，保留旧快照链接及历史差异；元数据、获取时间、变更摘要和验证边界写在快照外。向 `{维护知识库根目录}/wiki/log.md` 追加 `maintain` 记录，包含本轮授权、实际修改文件、版本、快照入口、哈希核验及未完成项；时间从本机读取并按该库规定的东八区格式记录，历史日志只追加。
- 交付前回读核对，分别报告“Skill 已修改”“完整版本已入库”“摘要／清单／索引已更新”和“日志已追加”。路径不可访问、授权不足、规则冲突、源目录变化或写入失败时，明确报告具体原因及已发生的改动；任一必要步骤未完成不得宣称整项维护完成，不得默默跳过或另建替代库。仅更新知识库记录不触发再次修改 Skill 或循环快照。
- 本规则由执行 AI 在同一维护任务内落实，不提供后台监听，不自动记录用户手动修改；使用 Skill 执行业务任务不触发 Skill 版本入库。它不授权覆盖 `.codex` 等其他 Skill 副本、补录未经核实的历史变更、修改其他知识主题或重构全库；这些操作另行确认范围。

- 实现后自检或用户要求独立审核：读取 [审核与授权](references/review.md)。
- 接手旧项目、补文档或交付：读取 [文档规范](references/documents.md)。
- 执行者接续、跨工具交接或能力核对：读取 [协作与能力适配](references/collaboration.md)。
- UE 实现、故障诊断、共享系统集成或代码审核涉及技术风险时：按需读取 [UE 技术检查](references/ue-technical-checks.md)。
- 功能修改完成且主智能体自检通过，并且涉及 C++／蓝图交接、蓝图资产或编辑器配置时：读取 [UE 技术检查](references/ue-technical-checks.md) 中的 C++／蓝图交付补充。
- 复杂任务记录或执行者交接：读取 [共用模板](references/templates.md)。
- 用户明确要求独立审核时：读取 [审核调用约定](references/reviewer-dispatch.md)。
