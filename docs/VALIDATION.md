# 验证范围与验收方法

## 发布候选状态

本仓库提供工作流、参考模板和角色示例，不包含完整的端到端运行认证。

| 项目 | 当前状态 |
|---|---|
| Markdown 引用、围栏、UTF-8 与发布文件范围 | 整理时进行本地检查 |
| Codex 角色 TOML 语法 | 使用标准 TOML 解析器检查 |
| Skill 和 ZCode 角色前言 | 检查已使用的简单字段格式；不等于客户端加载验证 |
| 不同客户端的角色发现与实际调用 | 待在使用者实际客户端验证 |
| 只读权限技术隔离 | 需要运行环境保证；配置示例不能代替实际检查 |
| UE 编译、PIE、二进制资产、存档或打包 | 未执行，不属于本仓库已有验证成果 |

此前指令边界测试中，独立子智能体在权限不足、未提供实际候选时拒绝了审核通过。这仅证明该次指令响应，不证明两端安装适配或只读沙箱已验证。

## 无工程写入测试

1. 在新会话中加载 Skill，指定实现端身份。
2. 明确只做测试，不允许任何工程或候选文件写入。
3. 请求主智能体核对 `ue-code-reviewer` 是否已加载，实际工具是否能选择该角色。
4. 核对审核者真实只读权限；不要用写真实工程文件的方式试探。
5. 提供一个纯文本需求与候选内容，要求主智能体实际调用审核者并等待返回。
6. 核对实际子任务标识、审核对象版本、审核结论及未验证项。

可使用的负向场景：

> 需求规定宝箱只发一次奖励。实现者声称候选已完成，但未提供补丁、基线或验证证据。请审核，禁止任何文件写入。

合理结果应为指出材料缺口、不能通过；未确认只读权限时还应报告权限阻塞。主智能体不应自行假定通过、伪造子任务或修改工程。

这只是负向测试，不能证明审核者能正确审查完整实现。通过后还需使用可核对的实际补丁做正向审核测试，随后在获准范围内验证真实 UE 任务。

## 问题反馈

反馈时提供客户端版本、工作流版本或文件标识、角色配置字段、复现步骤和脱敏后的结果。不要公开真实工程源码、敏感路径、账号配置、访问令牌或未获授权的日志。
